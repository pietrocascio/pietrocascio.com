## Post body

"You'll promote code review best practices."

Read that line from a job ad again. It doesn't say the team reviews code. It says you'll be the one
trying to make it happen.

Senior engineering job ads are full of sentences like this. Champion clean code. Raise testing
standards. Mentor juniors. Every verb describes something the hire is expected to bring, not
something the team already does.

That isn't necessarily dishonest. Ads get written from templates, often far from the codebase,
describing the team someone hopes to build.

But it does tell you where the gap is.

On the legacy systems I've worked on, the same three conditions showed up every time: no automated
tests, nobody owning the technical debt, and delivery always coming first.

They feed each other. Without tests, every change is risky. Risky changes make debt unpayable.
Nobody owns the debt, so nobody can trade delivery time to fix it. Delivery slows, pressure rises,
and the loop tightens.

A senior hire asked to "promote best practices" inside that loop needs exactly one thing: the
authority to spend delivery time breaking it.

So the useful interview question isn't "Do you do code review?" The answer is always yes.

Try this instead: "If I thought a merge request shouldn't go in, what would actually happen?"
