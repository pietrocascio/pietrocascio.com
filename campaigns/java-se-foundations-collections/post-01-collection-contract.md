## Post body

A logistics system that quietly loses packages. Duplicate IDs corrupting the warehouse. Code that
crashes the moment bad data shows up.

All of it traces back to one thing: an array being asked to do a job it was never built for.

I built a course with @Pluralsight around fixing exactly this. Published it a while back, then went
quiet about it — time to actually talk about what's in it.

The course follows Flux, a fictional package-routing engine, from "everything breaks" to "everything
is tracked, ordered, and type-safe." It starts with the most common Java habit there is: reaching
for ArrayList (or a plain array) without asking what the data actually needs.

Arrays store data. They don't manage change.

That one distinction is why the entire Collection Framework exists — and it's where the course
begins, before a single line of "correct" code shows up.

From there, Flux's data layer gets rebuilt module by module: Lists enforcing order, Sets enforcing
uniqueness, Maps enforcing identity, and the ordering guarantees SequencedCollection made
explicit in Java SE 21.

I won't walk through the fixes here — that's what the course is for.

What's the last "random" bug you debugged that turned out not to be random at all — just an
assumption about ordering nobody wrote down?
